## Session 1 — Pièces uniques et paiement (critique)

Principe commun : stocker sur la création qui détient le verrou (`reservedByReservationId` ou
`reservedBySessionId`) et ne libérer une pièce QUE si le verrou appartient encore à la réservation
qui la libère.

- [x] **Expiration Stripe non idempotente** — `lib/checkout-fulfillment.ts:461-500`. `releaseExpiredCheckoutSession` passe `status: "cancelled"` mais laisse `paymentStatus: "pending"` : un `checkout.session.expired` rejoué retrouve les mêmes réservations et remet `reserved:false` sur la pièce sans vérifier qui la détient (un autre acheteur l'a peut-être verrouillée). Corriger : `paymentStatus: "failed"` (ou `"expired"`) + filtre sur le détenteur du verrou.
- [x] **Pièce déjà vendue confirmée à un 2e acheteur** — `lib/checkout-fulfillment.ts:207-216`. Si `findOneAndUpdate({sold:{$ne:true}})` renvoie null, le code relit la création et traite la réservation comme payée + email « Paiement confirmé ». Corriger : marquer la réservation en conflit, rembourser (`stripe.refunds.create`) ou au minimum alerter l'admin, pas d'email de confirmation.
- [ ] **Annulation client trop permissive** — `app/api/account/reservations/[id]/cancel/route.ts:52-81`. Seul `validated` est bloqué : annulation d'une commande payée/expédiée sans remboursement, ré-annulation d'une réservation déjà annulée qui libère la pièce verrouillée par quelqu'un d'autre. Corriger : n'autoriser que `status === "pending"` et `paymentStatus !== "paid"`, de façon atomique (`findOneAndUpdate({_id, status:"pending"})`), libérer la pièce seulement si le verrou est le sien. Aussi : `reason` non-string fait planter après le `save()` (l. 97), id non ObjectId → 500. (La route n'est appelée par aucune page : envisager de la supprimer.)
- [ ] **Admin : annulation/suppression d'une ancienne commande remet en vente une pièce revendue** — `app/api/admin/reservations/[id]/route.ts:186-192` et `:318-325`. Ne remettre `sold:false` que si aucune autre réservation payée non annulée n'existe pour la pièce ; au DELETE d'une réservation déjà annulée, ne pas toucher la pièce. Libérer aussi `reserved` et les champs `reserved*` (sinon pièce bloquée après annulation d'une commande saisie par l'admin, `app/api/admin/reservations/route.ts:161-167`).
- [ ] **Webhook répond 200 sans avoir enregistré la commande** — `app/api/stripe/webhook/route.ts:60-65`. Si `fulfillCheckoutSession` renvoie `paid:false/pending:true` (ex. `paymentIntents.retrieve` en échec), répondre 500 pour que Stripe réessaie.
- [ ] **Relance du checkout** — `app/api/stripe/create-checkout-session/route.ts:212-248` + `lib/checkout-fulfillment.ts:184-187, 246`. Les anciennes réservations passent `failed` AVANT `sessions.expire`, dont l'échec est ignoré. Si l'ancienne session est quand même payée : client débité sans commande, puis débité une 2e fois. Corriger : expirer d'abord, `failed` seulement si succès, sinon 409 ; dans `fulfill`, session payée sans réservation en attente → alerte admin + remboursement.
- [ ] **Pièces cachées achetables** — `create-checkout-session/route.ts:58` et `:157-162` : ajouter `hidden: { $ne: true }`.
- [ ] **Route `/api/creations/[id]/reserve` exposée et inutilisée** — verrouille sans paiement ni expiration ni limite, ignore `hidden`, envoie un email à chaque appel. Supprimer (vérifier qu'aucune page ne l'appelle).
- [ ] **Emails de commande en double / perdus** — `lib/checkout-fulfillment.ts:155-244, 279`. Webhook et verify-session en parallèle → deux emails partiels avec frais de port comptés deux fois ; `Promise.all` qui rejette → emails jamais envoyés. Décider de l'envoi au niveau de la session (flag atomique) et construire l'email à partir de toutes les réservations + `session.amount_total` (corrige aussi le total recalculé au prix actuel, l. 275-280).
- [ ] **Filet de sécurité des verrous** : pas de cron, tout repose sur `checkout.session.expired`. Ajouter un cron Vercel qui libère les pièces `reserved` depuis > 35 min dont la session est expirée. Vérifier dans le dashboard Stripe que l'endpoint est abonné à `checkout.session.expired`.

## Session 2 — Compte, sécurité, front critique

- [ ] **Pré-prise de contrôle de compte** — `app/api/register/route.ts:41` + `authOptions.ts:26` (`allowDangerousEmailAccountLinking`). Inscription sans vérification d'email puis liaison Google automatique : l'attaquant garde son mot de passe sur le compte de la victime. Corriger : vérification d'email à l'inscription, ou refuser la liaison / supprimer le mot de passe quand l'email n'est pas vérifié.
- [ ] **Open redirect après connexion** — `app/login/LoginForm.tsx:17, 54` : n'accepter que `cb.startsWith("/") && !cb.startsWith("//")`. Même validation dans `app/login/page.tsx:15` (utilisateur déjà connecté renvoyé vers `/` au lieu du callbackUrl). Le Header envoie toujours `callbackUrl=/` : passer le chemin courant.
- [ ] **Correctif MongoDB incomplet** — `lib/mongodb.ts:15` : `clientPromise` est figé au chargement, l'adaptateur garde la promesse rejetée. Exporter `getClientPromise()` et `MongoDBAdapter(() => getClientPromise())`.
- [ ] **Upload Cloudinary non signé** — `hooks/useImageUpload.ts:4, 30` : route `/api/admin/cloudinary-signature` (admin), preset en « signed » côté Cloudinary, retirer `NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET`. Action manuelle côté Cloudinary.
- [ ] **Suppression d'une création efface les commandes payées** — `app/api/creations/[id]/route.ts:324` : refuser s'il existe des réservations payées, proposer `hidden:true`.
- [ ] **Contact = relais de spam** — `app/api/contact/route.ts:73, 92, 211-221` : email de confirmation à n'importe quelle adresse avec `name`/`subject` libres, rate limit en mémoire indexé sur l'email. Valider le format, limiter par IP (règle pare-feu Vercel ou stockage partagé), honeypot, ne pas reprendre name/subject dans la confirmation. Aussi : pas de validation de type (`creationId` invalide → 500, `email: 123` → crash, `creationIds` non borné), retour du document Contact complet (l. 228), `subject` non nettoyé dans l'objet du mail admin (l. 186), champs création non échappés (l. 154-166).
- [ ] **Filtres anti-spam/insultes trop agressifs** — `app/api/contact/route.ts:46, 55, 57` : « fils de laine », « conçu » (`\bcon\b` avec ç), numéros de téléphone rejetés. Retirer ces motifs, frontières Unicode.
- [ ] **Article réservé affiché disponible** — `app/page.tsx:55-69`, `app/creations/[id]/page.tsx:145-161`, `CreationDetail.tsx:405` : exposer `reserved`, badge « Réservé », bouton désactivé, filtre « Disponibles » cohérent.
- [ ] **Retrait sur place perdu à chaque visite** : voir « Bugs trouvés en écrivant les tests ».
- [ ] **Rate limiting auth** : aucune limite sur `/api/auth/callback/credentials`, `/api/register` ; celle de forgot-password est en mémoire par email. Règles pare-feu Vercel (action manuelle) ou limite par IP partagée.
